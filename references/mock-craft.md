# Stage E：可信证明面（Mock & Proof Surfaces）

Mock 不是“假截图”，是从产品源码推导出的信息架构可视化。目标是让访客感受到真实能力和状态，而不需要安装。先完成 `content-to-modules.md` 的模块契约；只有当 mock 是最合适的证明形式时才制作。

---

## E1. 从源码推导 mock 信息架构

Mock 的内容必须来自产品本身，不是设计师的想象。

**推导步骤：**

1. **读入口文件**：`main.rs` / `cli/mod.rs` / `package.json` 的 bin 段 / `App.tsx` 的路由——产品的真实能力边界在这里。
2. **跑 `--help` 或读 CLI 定义**：真实命令输出是最强的 mock 素材。把输出原样放进终端 mock，不删减、不美化。
3. **读数据结构**：DTO（`types.ts` / `mod.rs` 的 DTO 段）决定了界面的信息密度。mock 里的每一条数据都要和 DTO 字段一一对应。
4. **读状态枚举**：`status: "ok" | "error" | "syncing"` → mock 要展示真实状态，不全是 happy path。

**红线：mock 里的每一个字段、状态和行为都要能追溯到源码、demo 数据或验证过的命令输出。** 具体记录可以是合成的，但必须在面板内明确标注“合成数据”，不得冒充已连接账户、真实执行结果或产品指标。

### 动态 mock 与截图的诚信边界

- 需要证明交互、状态变化或操作边界时，优先使用可追溯的动态 mock。
- 需要证明实际 UI 外观或像素忠实度时，使用真实截图或录屏。
- 动态 mock 不得声称是“真实界面截取”；用“交互式演示”、“合成数据”等准确描述。
- 截图可以仅作为 `og:image` 社交预览，不必因此成为页面主体。

## E2. 细节密度法则

mock 的可信度和细节密度成正比。但"多"不等于"密"——关键是**真实的杂**。

### 条目数服从证明目标

完整产品列表需要足够密度来建立可信感；紧凑的 Hero 或手机面板可以只展示少量代表性条目。不要为了固定数量牺牲可读性。关键是数据具体、层级真实、状态有差异，并与模块的叙事任务相称。

### 状态要杂

不要全是 "installed ✓"。混合展示：
- 3 个已安装（`installed`）
- 2 个可更新（`update available`）
- 1 个未安装（`not installed`）
- 1 个同步中（`syncing...`）

这比 7 个全绿更真实。

### 文案要具体

❌ "Tool 1"、"Skill Alpha"
✅ "claude_code"、"readme-please"、"github-pages-legacy-deploy"

真实项目名、真实路径、真实数字。模糊 = 假。

### 层级服从交互任务

复杂 mock 通常需要概览、详情和交互三个层级；紧凑证明面可以减少层级，只要仍能完成模块契约中的任务：
- **L1 概览**：名称 + 状态（"readme-please · synced"）
- **L2 详情**：路径 + 工具 + 最后同步时间（"~/.skillshub/readme-please → workbuddy · 2h ago"）
- **L3 交互**：可点击/可复制的元素（"copy install prompt" 按钮）

## E3. 桌面应用 mock 规范

Mock 应忠实于实际产品的信息架构。真实产品使用顶部 tab 就使用顶部 tab，使用侧栏就使用侧栏；不要为了套用落地页惯例而改写产品结构。移动端可以按照 `responsive-choreography.md` 使用摘要、重排或替代交互。

### Tab 布局结构

```
┌─────────────────────────────────────────┐
│  [My Skills]  [Explore]  [Settings]     │  ← 顶部 tab
├─────────────────────────────────────────┤
│                                         │
│  内容区域（每个 tab 一种信息架构）        │
│                                         │
└─────────────────────────────────────────┘
```

每个 tab 的内容区域是独立的 mock，信息架构从对应的功能模块源码推导。

### Mock 不要全屏

桌面 mock 放在页面布局的自然位置（如 hero 右侧、特性区中央），保留周围的文案和留白。全屏 mock 没有上下文，访客不知道它在展示什么。

## E4. 终端 mock 规范

终端 mock 是 CLI/agent 产品的核心证明面。制作规则：

### 内容必须真实

- 命令输入 = 真实命令（`skilldo list --json`）
- 输出 = 真实输出（或从真实输出精简，但不编造）
- 错误状态也要展示（如 `repository not found`）

### 打字动画

终端逐行 reveal 是最有效的 reveal 类动效。实现要点：
- 每行延迟递增（`--d: 0.15s` 递增）
- 光标跟随最后一行（`blink` 动画）
- 命令行先出现命令文本，再出现输出（模拟真实执行）
- `prefers-reduced-motion` 时所有行直接显示，无动画

### 终端 chrome

终端窗口的外壳（标题栏、按钮、圆角）要简洁：
- 标题栏只放三个点（红黄绿）和窗口标题
- 不要终端仿真器的全部 UI（菜单栏、滚动条、分屏按钮）
- 背景色用设计 token 的 `--panel`，不用 `--bg`

## E5. 截图 vs mock 决策

| 情况 | 选择 | 理由 |
|---|---|---|
| 有高质量产品截图 | 用截图 | 真实 > 制作 |
| 截图过时或质量差 | 用 mock | 过时截图比没有更糟 |
| 产品未发布 / UI 未成型 | 用 mock | mock 可以展示信息架构而非具体样式 |
| 需要展示多种状态 | 用 mock | 截图只能捕捉一个状态 |
| 需要展示代码/命令 | 用终端 mock | 比截图更清晰、可动画 |

**原则：宁缺毋滥。** 如果 mock 的信息密度不够、状态不够真实、数据不够具体，宁可不放 mock，用文字和数字代替。一个低质量的 mock 比没有 mock 更伤可信度。

## E6. 落地清单

- [ ] 每个 mock 的数据都能追溯到源码（字段 / 命令输出）
- [ ] 列表密度适合叙事任务和视口，并混合真实状态
- [ ] 文案用真实项目名/路径/数字
- [ ] mock 的导航和信息架构可追溯到真实产品
- [ ] 终端 mock 内容真实，有打字动画且有降级
- [ ] mock 放在自然布局位置，非全屏
- [ ] 无产品截图时，mock 信息密度足够支撑可信度
