# Stage A/B：项目考古与创意简报

落地页的大多数结构性问题在实现前就可以避免。这一份参考覆盖证据、文案和叙事：先像产品考古学家一样读懂项目，再产出与当前创作自由度相称的简报。只有存在真正的方向分支时才需要多个方向提案。

---

## A1. 三层翻译：从"它有什么"到"你得到什么"

README 写的是功能，落地页卖的是获得。逐条做三层翻译：

| 层 | 内容 | 示例（skilldo） |
|---|---|---|
| L1 功能 | README 原文怎么说 | "统一管理 45 个工具的 skills" |
| L2 获得 | 用户的生活因此变成什么样 | "不用再记五套 skill 目录" |
| L3 情绪 | 这个获得让用户感觉什么 | "所有 agent 的能力，一处收拢" |

落地页正文只用 L2/L3；L1 退到快速开始、对比表、技术细节区。**如果你的 hero 主标题写的是 L1，说明翻译还没做完。**

实操：把 README 的 feature list 全部抄下来，逐条写 L2。写不出 L2 的功能是"列表凑数功能"，直接砍掉不上首页。

## A2. 源码事实核实（evidence-first 数字）

页面上每个数字、每个能力声明必须可溯源。方法：

1. **数枚举**：能力数量去源码数（如 Rust `enum ToolId` 的变体数、CLI 子命令数）。数完记录文件路径和行号。
2. **跑 `--help`**：真实命令输出直接可以当终端 mock 素材，比编造的强十倍。
3. **读入口**：`main.rs`/`cli/mod.rs`/`package.json` bin 段——产品的真实能力边界在这里，不在 README 的愿景段。
4. **读测试**：测试用例是最诚实的能力清单（什么被测 = 什么真的能用）。
5. **看 assets**：logo、截图、demo 是仅有的可以直接引用的视觉证据；记录它们的路径和色彩值。

红线：不可编造采用量、用户评价、集成列表、性能数字。没有证据就换一个能被证据支撑的说法，或者干脆不放。

## A3. 调性信号采集

"调性"不是拍脑袋定的，是从项目自身采集的。开始设计前过一遍这张表：

| 信号来源 | 采集什么 | 影响什么 |
|---|---|---|
| 项目命名 | 直白（`cleanup`）还是造词（`skilldo`）？中文/英文/混合？ | 文案的词汇域、是否可用俚语 |
| commit message | 规规矩矩的 conventional commits，还是随性口语？ | 页面语气：克制 ↔ 俏皮 |
| README 行文 | 教科书式 / 教程式 / 命令式？句长？中英混排习惯？ | 文案句式节奏 |
| logo 与色彩 | 主色、几何语言（圆角/直角/线条粗细）、明暗适应性 | token 的 accent、圆角半径、边框语言 |
| 产品类型 | CLI / 桌面应用 / SaaS / 库 | 整体风格方向的先验 |
| 目标用户画像 | 给开发者的可以硬核，给大众的要低门槛 | 术语密度、CTA 措辞（"clone" vs "免费开始"） |

**核心承诺**（hero 要卖的那一件事）：

## B1. 叙事弧（narrative arc）

在写任何一行 HTML 之前，先写下访客的心理路径。一页落地页是一部三幕剧：

```
进场（0–5s）   → 访客带着什么问题来？第一眼要让他相信什么？
展开（滚动）   → 用什么证据顺序消除怀疑？先共情痛点还是先秀能力？
高潮与收束     → signature moment 在哪一屏爆发？CTA 前最后一句说什么？
```

写成 4–6 行的弧线文本，例（skilldo）：
1. 进场：开发者已被多 agent 多目录折磨 → "你的 skills，该有个家了"
2. 展开一：能力证据（工具矩阵 + 终端实拍）
3. 展开二：机制可视化（收拢→软链→各工具读取）
4. 高潮：所有 skill 卡片被吸入一个黑洞般的 hub —— 产品隐喻的物理化
5. 收束："对 AI 说一句话"即可安装 → 复制 prompt 的 CTA

每一屏只为弧线上的一步服务。一屏想说两件事，就拆成两屏。

## B2. 文案声音系统（voice system）

调性先声明，再写文案。三个决定：

**① 调性光谱定位**（1–5 打分）：

```
克制专业 1 ─ 2 ─ 3 ─ 4 ─ 5 自信俏皮
```

判据：产品类型（infra→1，开发者工具新品→3，消费级→4）+ 调性信号（A3）。定完写一句调性声明，如："工程可信的底子，允许一两处会心一笑的巧劲。"

**② 声音指南**（写下来，全页遵守）：
- 人称：对"你"说话（第二人称），产品名做主语时用"它"且每屏最多一次
- 动词力度：CTA 和标题用强动词（收拢、清出、装上），说明文字用中性动词
- 句长节奏：标题 ≤14 字，lead 1–2 句，正文每段 ≤3 行
- 禁词：赋能、抓手、极致、一站式、革命性——以及一切 README 里不会出现的词

**③ 双语规则**：中英不是直译关系，是同一叙事弧的两次地道化。英文可以更短促直接；中文可以用口语节奏（"对 AI 说一句话，清出 Mac 里沉睡的空间"）。技术名词两边保持一致（tool 名、命令、路径不翻译）。

## B3. 交互概念：产品核心动作的页面化预演

这是"有趣灵活的交互体验"的正源。方法：**找到产品的核心动作，让访客在页面里预演它。**

| 产品核心动作 | 页面化预演 | 实际案例 |
|---|---|---|
| 对 AI 说一句话完成安装 | 页面上就放一条可复制的自然语言 prompt，按钮=复制 | skilldo 安装 CTA |
| 命令行执行 | 终端 mock 逐行打出真实输出 | skilldo hero 右侧 |
| 把分散的东西收拢 | 滚动终章：卡片被引力吸向一个中心 | skilldo 黑洞终章 |
| 数据实时变化 | 数字滚动到真实值 | 通用 |
| 文件从 A 到 B | 拖拽/飞行动画演示路径 | 通用 |

先填表再设计交互。如果一个交互不在"预演产品动作"之列、也不在动效意图四分类（见 motion-choreography.md）之列，它就是装饰，砍掉。

## B4. Motion emphasis 提案

建立明确的动效注意力层级。通常选择一个主要记忆点放在叙事高潮位，其他动态场景为它服务；当产品确有多个独立机制需要证明时，可以增加强场景，但不能让它们同时争夺注意力。提案时回答四问：

1. **隐喻**：它把产品的哪个抽象概念变成了可见物理？
2. **时机**：访客滚到第几屏、停留第几秒遇到它？
3. **不可截图性**：动图/视频能否传达它的 50%？（不能的话它依赖滚动时序，要确保静态降级也可看）
4. **成本**：需要什么技术（纯 CSS / GSAP / Three.js）？移动端等价物是什么？

skilldo 黑洞终章的四问答案：隐喻="所有 skill 收拢进一个 hub"；时机=最后一屏（叙事完成后的收束）；不可截图性=中等（静态时也要呈现出"汇聚成一点"的构图）；成本=GSAP + matchMedia 桌面限定，移动端给静态汇聚构图。

## B5. 方向提案（按需）

当项目存在重大但未解决的视觉或结构分支时，产出少量**真正不同**的方向，交给用户选择。项目已有明确设计语言时，直接提出一个有证据的推荐方向并说明依据。每个方向一屏内说清：

```md
### 方向一：「终端考古」
概念一句话：把安装过程做成一场可以围观的操作。
结构草图：hero(终端逐行 reveal) → 工具矩阵 → 机制图 → 快速开始
风格家族：终端美学（design-directions.md #1），深色优先
动效野心：低—中（CSS 为主）
风险：与众多 CLI 落地页同质，差异化靠文案与矩阵设计

### 方向二：「引力叙事」
概念一句话：整页讲"收拢"这一个动词，终章黑洞汇聚。
...
```

规则：
- 多个方向必须在风格家族、结构、动效野心上**实质不同**，不是同一路子的三档配色
- 每个方向都要基于 dossier 的事实，不出现没证据的能力
- 用户选定后，后续设计以该方向的宣言为依据；如果核心方向改变，重新检查文案、模块和响应式方案是否仍成立
